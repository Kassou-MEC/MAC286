1 · First things first: what is "complexity"? no code yet

Before a single line of Java, let's agree on what we are even talking about. Imagine two programs that both find a name in a list of a million customers. Both give the correct answer. One responds instantly; the other makes you wait. Same computer, same data, same answer — the difference is the algorithm: the step-by-step recipe each program follows. Complexity is how we describe the cost of a recipe.

Time complexity
What it means
Time complexity measures how the runtime of an algorithm increases as the input size grows.
In other words
It's like asking: "If I double my data, will my program take twice as long — or will it completely melt down?" 🔥
Space complexity
What it means
Space complexity measures how much memory an algorithm uses as the input size increases.
In other words
Think of it as: "Will my program eat all my RAM like Cookie Monster eats cookies?" 🍪
Big-O notationthe vocabulary
What it is
The shared vocabulary for naming growth patterns. Instead of "the work grows in direct proportion to the input", programmers everywhere just say O(n).
How to read it
Say "Big O of n". n is the input's size; whatever sits inside the parentheses is the growth shape.
One honest rule
Big-O describes the worst-case scenario. It’s pessimistic — like assuming every traffic light will be red on your way to work! (Section 6 makes the cases precise. It also ignores small constants: a loop doing 2 steps per element is still O(n).)

Here is the whole family you will meet in this lecture, slowest-growing first. Skim it now; each one gets its own definition, everyday picture, and runnable Java program below.

O(1)constant

Same work no matter the size. Walking straight to mailbox #305.

O(log n)logarithmic

Each step halves the problem. The number-guessing game with higher/lower hints.

O(n)linear

Touch everything once. Reading every page of a book.

O(n log n)linearithmic

A log-n job for each of n items. What good sorting costs.

O(n²)quadratic

Everything meets everything. Every student shaking every hand.

The same family as a picture. The x-axis is the input size n (how much data you hand the algorithm); the y-axis is the operations (how much work it does in return):

Why you should care: for n = 1,000,000 items, an O(log n) recipe does about 20 steps, an O(n) recipe a million, and an O(n²) recipe a trillion. Same computer — the recipe alone is the difference between instant and impossible. Naming these shapes is the skill this lecture builds.

3 · O(1) and O(n): flat versus straight line the first two shapes

Big-O notation is just a short name for the growth pattern you counted in the warm-up. We start with the two friendliest shapes. O(1), "order one", means constant: the step count does not change when the input grows. O(n), "order n", means linear: double the input, double the work — a straight line.

Big idea: Big-O ignores small details on purpose. A loop that does 2 additions per element is still O(n), not "O(2n)" — because when n gets huge, the 2 is pocket change and the shape is what decides whether your program finishes in a blink or an hour.
O(1)"Big O of one" — constant time
on the Section 1 chart: the flat teal line along the bottom
What it means
The step count stays the SAME no matter how big the input gets — the one operation that never slows down.
Everyday picture
Mailbox #305 out of 500: you walk straight to it and never touch the other 499.
How to spot it in code
No loop over the input: a[5], simple math, an assignment.
O(n)"Big O of n" — linear time
on the Section 1 chart: the straight amber diagonal
What it means
Steps grow in direct proportion: double the data, double the work — the honest price of touching every element once.
Everyday picture
A letter is lost somewhere in the 500 mailboxes: open them one by one.
How to spot it in code
ONE loop that visits every element.

4 · O(n²): a loop inside a loop the danger zone

Here is the most common way to accidentally write slow code: nest one loop inside another, both walking the same array. Each of the n elements gets paired with the others — roughly n × n work. We will count the comparisons and watch the n² shape appear.

Big idea: the fingerprint of O(n²): double the input → about four times the work. Below, 5 elements need 10 comparisons but 10 elements need 45. At n = 1000 that is already about half a million comparisons — quadratic code feels fine in testing and explodes in production.
O(n²)"Big O of n squared" — quadratic time
on the Section 1 chart: the red curve that leaves the chart before n reaches 8
What it means
Work grows like size × size: double the input, about FOUR times the work. Feels fine on test data, chokes on real data.
Everyday picture
Everyone in class shakes everyone's hand: 10 students = 45 handshakes, 20 students = 190.
How to spot it in code
A loop INSIDE a loop, both walking the input.

5 · O(log n): cut the problem in half the happy one

Now the opposite of the danger zone — the happiest complexity there is. It comes from one move: every step throws away half of what is left. Binary search (from the Advanced Arrays lecture) is the classic example; here it returns with a guess counter on board.

Big idea: log n is not scary math. It just answers: how many times can I cut n in half before nothing is left? 16 → 8 → 4 → 2 → 1 is four cuts. A million only takes about twenty. That is why doubling the array adds just one guess.
O(log n)"Big O of log n" — logarithmic time
on the Section 1 chart: the blue curve that barely rises
What it means
log n just answers: how many times can I cut n in half? Work grows that slowly — doubling the input adds only ONE step.
Everyday picture
Guess my number from 1 to 100 with higher/lower hints: 7 guesses at most. From 1 to a million: about 20.
How to spot it in code
The remaining range keeps HALVING (binary search), or a loop variable DOUBLES: i = i * 2.

The guessing game in Java is binary search, which you met in the Advanced Arrays lecture. Here it is again with a guess counter, so the astonishing numbers print themselves:

6 · Best, average, and worst case same code, different luck

One algorithm can be fast and slow — it depends on the input it happens to meet. Linear search finds a target in 1 check if it is lucky and n checks if it is not. That is why we name three cases, and why Big-O usually describes the worst one: it is the promise your code can always keep.

Big idea: when someone says "linear search is O(n)", they mean: even on its unluckiest day it does about n checks. Best case (O(1) here) is nice to know, but you cannot plan around luck.
Best / average / worst case
Best case
The luckiest input — the target in the very first box. You cannot plan around luck.
Average case
A typical input — about n / 2 checks for linear search.
Worst case
The unluckiest input — every box checked. An unlabeled Big-O means THIS case: the promise kept no matter what.

7 · The growth table: why any of this matters see the shapes

Time to put the shapes side by side. This program computes log n the honest way — by counting halvings — and prints one row per size as n doubles from 8 to 1024. Read the table column by column and watch each shape pull away from the last.

Big idea: at n = 1024, the columns read 10 (log n), 10,240 (n log n) and 1,048,576 (n²). Same input, a hundred-fold gap between good and bad — and the gap only widens. This is why replacing an O(n²) idea with an O(n log n) one (Practice Problem 2) is worth real money.
O(n log n)"Big O of n log n" — linearithmic time
on the Section 1 chart: the orange curve between the diagonal and the red one
What it means
A log-n-sized job done for EACH of n items. More than linear, massively less than quadratic.
Where you will meet it
Good sorting: merge sort and Arrays.sort(). It is the price Practice Problem 2 pays for sorting first.
Everyday picture
Sorting a deck by splitting it into halves (log n rounds) and merging them back (n work per round).

8 · Space complexity: the memory bill the other cost

Time is not the only thing an algorithm spends. Space complexity asks: how much extra memory does the method need, beyond the input it was given? Here are two correct ways to reverse an array — same result, very different memory bills.

Big idea: O(1) space means a fixed handful of variables, whatever the input size. O(n) space means the extra memory grows with the input — like building a whole second array. Neither is "wrong": in-place is cheaper, the copy keeps the original safe. Knowing the price lets you choose.
O(1) vs O(n) space
O(1) extra space
A fixed handful of variables, whatever the input size — the shelf shuffled in place.
O(n) extra space
Extra memory that grows with the input — typically a whole second array. The second shelf.
Why both exist
Neither is wrong: in-place is cheaper, the copy keeps the original safe. Know the price, choose on purpose.

9 · Measuring for real, with a stopwatch theory meets clock

Counters prove the theory; a clock shows it costs real seconds. System.nanoTime() reads the computer's clock in billionths of a second. We time our O(n²) method at three sizes, each double the last — and the theory predicts each timing should be about four times the previous one.

Big idea: exact milliseconds vary from computer to computer and even run to run — that is normal. The ratio between rows is what confirms the complexity. Doubling n → roughly 4× the time is O(n²) shaking your hand.
